# Prefix Cache 分项实验

基线为研究分支的 `b2f0218`。本轮从学习器开始，价值公式和叶节点索引沿用基线。正式推理采用单请求顺序回放，消除四并发实验中同批请求到达顺序不同的影响。

## 第一阶段　在线学习器

本阶段检验三个不同的问题：预测概率是否更接近后续实际复用，预测变化是否改变固定资源条件下的缓存命中，以及用户实际等待首个 token 的时间是否改善。

| 层次 | 只改变什么 | 如何判断 |
| --- | --- | --- |
| 概率预测 | 冻结权重、学习率 0.01/0.03/0.10；在 0.03 下单独屏蔽频率、间隔或深度特征 | 每次请求结束时保存概率，等后续请求给出标签，再计算 Brier 分数和对数损失，越低越好。屏蔽深度时，外层价值公式仍使用原深度。 |
| 缓存回放 | 冻结与三档学习率；每组冷启动并使用相同请求和逻辑时间 | 按请求比较复用 token 数与实际淘汰；记录容量、锁和叶索引一致性。 |
| 本机 GPU | 冻结、默认 0.03、较快 0.10；相同模型、配置和负载 | 新种子 1735，顺序运行“默认、冻结、较快、较快、冻结、默认”。每组预热 24 次，清空 KV 与权重，再计 240 个请求；比较 TTFT P95、逐请求命中与生成文本、学习与淘汰管理耗时。 |

离线实验的开发种子为 1729–1731，留出种子为 1732–1734，各自从零权重开始。学习率按开发种子的平均 Brier 分数选择。GPU 使用预先指定的学习率对照；即便离线排序不同，也保留固定顺序和配置。三项测试均使用同一类合成热点切换负载，跨种子验证仅覆盖这一负载族。

固定时钟回放测试 2048/4096 token 两种容量、0.01/0.1/1 秒三种请求间隔。同一条轨迹改变间隔会改变 LRU 时间戳差距，而保留奖励最多只改变 1 秒排序分，因此按间隔单独解释结果。每个容量和间隔都使用同一批种子，不能当作互相独立的大样本。

### 概率预测和单特征消融

Brier 分数是预测概率与实际 0/1 标签间的均方误差。开发集三种子按种子等权平均，0.01、0.03、0.10 的分数依次是 0.172814、0.154284、0.139942，因此 0.10 进入候选。留出集在早期诊断中曾经跑过；本轮选择只使用开发数据。

| 设置 | 留出 Brier（越低越好） |
| --- | ---: |
| 全部权重冻结，概率固定 0.5 | 0.250000 |
| 全特征，学习率 0.03 | 0.144530 |
| 仅去掉访问频率，学习率 0.03 | 0.146314 |
| 仅去掉上次复用间隔，学习率 0.03 | 0.172563 |
| 仅去掉前缀深度，学习率 0.03 | 0.145019 |
| 仅保留偏置，学习率 0.03 | 0.175988 |
| 全特征，学习率 0.10 | 0.131636 |

同一学习率下，屏蔽复用间隔带来最大的 Brier 回退（+0.028033），屏蔽深度的影响较小（+0.000489）。这是预测器输入的重要性，对外层深度奖励的判断需要另做消融。

回放末尾有些新预测只来得及见到早出现的正例。限制为看完完整未来窗口的预测后，0.03→0.10 的留出 Brier 仍下降（0.170483→0.158448），但对高置信错误更敏感的对数损失上升（0.526033→0.542096）。因此“较高学习率更好”取决于指标，在 GPU 和跨负载证据充分前保留 0.03 为默认值。

按相同种子、前缀和预测时刻逐条配对，完整窗口有 3,712 个成熟标签。其中 996 个前缀未在之后的 64 个请求内再次出现。在这 996 个负例里，模型却给出至少 90% 复用概率的次数从 **61 增至 330**。按全部事件计算，正例的平均对数损失从 0.24149 降至 0.18447，负例的平均对数损失从 1.30189 升至 1.51669。这解释了 Brier 改善而对数损失回退：高学习率让不少预测更准，也让一部分错误预测更自信。这些事件来自前缀采样，数量不同于独立请求数。

### 固定时钟的缓存命中

36 种场景各执行四种配置，每种配置回放 240 个请求，共 34,560 次正式请求回放。另从空缓存重跑全部配置，逐请求复用、容量和训练状态的校验摘要在 144 组中均吻合。六条输入序列与预测评估使用的序列逐项核对相同。

| 候选与对照 | 开发场景（多／平／少） | 留出场景（多／平／少） |
| --- | ---: | ---: |
| 学习率 0.10 对 0.03 | 6／9／3 | 9／6／3 |
| 学习率 0.10 对冻结 | 12／6／0 | 11／6／1 |
| 学习率 0.03 对冻结 | 12／6／0 | 11／6／1 |
| 学习率 0.01 对 0.03 | 2／6／10 | 2／6／10 |

表中“多／平／少”按每个场景的总复用 token 与对照比较。留出场景中，从默认 0.03 调到 0.10 合计多复用 6,913 个 token，仍有 3 个场景回退。1 秒间隔下各配置总复用数一致。每次请求的逻辑时间由回放设定，这些结果用于解释淘汰行为，GPU 时延另测。

### GPU 正反序对照

同一输入、单请求顺序回放，每组 240 个请求均成功完成，6 组合计 1,440 个正式请求，实际模型及 KV 容量相同。第二轮按相反顺序运行；下表按策略对应，以同轮默认 0.03 为参照。

| 条件 | TTFT P95 第1／2轮（ms） | 复用 token 数第1／2轮 | 命中不同的请求数第1／2轮 | 文本不同的请求数第1／2轮 |
| --- | ---: | ---: | ---: | ---: |
| 默认 0.03 | 160.18／161.34 | 40,448／40,448 | 基准 | 基准 |
| 冻结权重 | 158.18／159.81 | 40,448／40,448 | 0／0 | 0／0 |
| 较快 0.10 | 159.35／157.65 | 41,216／41,728 | 2／3 | 1／1 |

0.10 的 P95 两轮分别低 0.83 ms（−0.52%）和 3.69 ms（−2.29%）。第一轮多复用的 768 个 token 来自请求 188（0→512）和 219（0→256）；第二轮另有请求 179（0→512），共多复用 1,280 个 token。两次 0.10 运行最终权重相同，生成文本彼此完全一致。每次与默认组比较，均有请求 219 的文本不同，两边都生成了完整的 16 个 token。默认组服务端相邻请求的到达间隔中位数约 0.65 秒，固定顺序仍允许实际的墙钟时间不同。

分组尾部有回退，例如首轮前缀组 3（5 请求）的 P95 较默认组高 38.72 ms，第二轮前缀组 4（10 请求）高 40.72 ms。小组分位数对个别请求敏感。本次证据支持在这条负载上将 0.10 作为候选；两轮 P95 差距、置信错误及输出差异均保留，生产默认仍为 0.03。[六组 GPU 明细、学习状态和逐请求差异编号](results/prefix_value_learner_gpu_20261127.json)。

## 第二阶段　价值公式实验方案

固定学习率 0.03、全部预测特征、叶节点索引、训练标签和 1 秒奖励上限，逐项移除外层评分因子。CPU 仍使用第一阶段的 36 种工作负载，配对基准改为完整公式。逐请求验证模型权重和标签计数一致，再比较缓存命中和淘汰结果。

| 条件 | 淘汰排序分（t 为末次访问时间） |
| --- | --- |
| full | t + min(p × 年龄衰减 × 深度倍率, 1) |
| no_depth | t + min(p × 年龄衰减, 1) |
| no_decay | t + min(p × 深度倍率, 1) |
| no_bonus | t；仍观测请求并更新权重 |

GPU 对照预先选定外层深度倍率，因为它直接回答“已经向预测器输入前缀深度后，还需要额外给深前缀加分吗”。同一学习率下采用 full、no_depth、no_depth、full 的顺序，使用种子 1735 的 240 个顺序请求，分别报告两轮的复用量和首 token 时延。只有在运行时配置、完整响应和学习状态都通过核对后，数据才纳入报告。

### 固定时钟结果

36 个工作负载的 144 次正式回放及 144 次复测已完成。所有组的逐请求训练权重和标签都对齐；完整公式的复用量与第一阶段 0.03 基线在 36 个场景中逐一吻合。

| 相对完整公式 | 开发场景（多／平／少） | 留出场景（多／平／少） | 留出复用量合计变化 |
| --- | ---: | ---: | ---: |
| 移除外层深度倍率 | 5／8／5 | 5／11／2 | +3,329 token（+0.34%） |
| 移除外层年龄衰减 | 6／8／4 | 7／7／4 | +1,281 token（+0.13%） |
| 移除全部奖励，按最近时间排序 | 2／6／10 | 1／6／11 | −39,168 token（−3.96%） |

这些百分比是 18 个留出场景的总复用 token 之差除以基准总数。禁用全部奖励后，11 个场景复用量下降；单独去掉深度倍率时，有 11 个场景持平，另有 2 个回退。1 秒请求间隔的 12 个开发和留出场景全部持平。价值奖励整体在部分压力条件下有效；深度倍率单独带来的收益仍未稳定。[价值项配对数据与复现信息](results/prefix_value_term_cpu_20261127.json)。
